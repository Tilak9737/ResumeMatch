# ResumeMatch Day 4 Implementation Plan

This plan details the implementation for Day 4 of the ResumeMatch sprint: **Deployment**. Having built a robust, tested NLP engine in Days 1-3, the goal for Day 4 is to get it live. We will wrap the repository in production-grade documentation, solidify dependencies, harden the application, and deploy it to a public URL so real users can access it.

> [!IMPORTANT]
> **UI Freeze:** We will NOT merge the Day 5 UI updates into Day 4. The current UI (Day 2) remains unchanged. Day 4's entire focus is proving the backend is stable in production.

## Proposed Changes

### 1. Dependency Management
- **[NEW] `requirements.txt`**: Pin tested production dependencies only.
  ```text
  streamlit
  pdfplumber
  scikit-learn
  ```
- **[NEW] `requirements-dev.txt`**: Separate development/testing dependencies.
  ```text
  pytest
  pytest-cov
  ```

### 2. Repository Hardening
- **`.gitignore`**: Ensure no secrets, no personal resumes, no debug files, and no local absolute paths are tracked.
- **Repository Clean-up**: Verify the repository is clean before deployment.

### 3. Documentation & Methodology
- **[NEW] `README.md`**: Create a comprehensive GitHub-ready README containing:
  - Product pitch ("See how well your resume matches a job before you apply.")
  - Architecture and Methodology (explaining the 30/30/20/10 Provisional Scoring)
  - Limitations (Not an ATS predictor)
  - Local installation and deployment instructions.
- **[NEW] Privacy Notice** (UI/Docs):
  > **ResumeMatch does not intentionally persist uploaded resumes or job descriptions as part of its application logic. Uploaded files are processed temporarily for analysis and removed after processing. Do not upload sensitive personal information you are uncomfortable processing through a third-party hosted service.**

### 4. Production Hardening
- **Pathing**: Ensure all data loads (e.g., `data/skills.json`) use relative paths.
- **File Cleanup**: Verify temporary PDF files are correctly cleaned up after extraction.
- **Configuration**: Verify the existing `.streamlit/config.toml` works in the deployed environment.

### 5. Deployment Flow
Follow this exact sequence:
1. Push the complete Day 1-4 codebase to GitHub.
2. Configure Streamlit Community Cloud (select repo, branch, and entrypoint).
3. Deploy and obtain the Public URL.
4. Verify dependency installation and application startup.

### 6. Production QA & Smoke Test
Once the public URL is live, perform a clean browser (incognito) deployment smoke test:
1. Open URL -> Upload real resume -> Paste JD -> Analyze -> Similarity appears -> No server error -> Refresh -> Run another analysis.

**Production PDF Test Matrix:**
| PDF                  | Expected         |
| -------------------- | ---------------- |
| 1-page normal resume | ✅                |
| 2–3 page resume      | ✅                |
| Unicode characters   | ✅                |
| C++ / C# / .NET      | ✅                |
| Multi-column resume  | Test             |
| Tables               | Test             |
| Empty PDF            | Controlled error |
| Corrupt PDF          | Controlled error |
| Scanned PDF          | Controlled error |
| Very large PDF       | Controlled error |
| Weird spacing        | Test             |

### 7. Release Tagging
- Once QA is complete, tag the repository: `git tag v0.4.0-day4-deployed` to freeze the Day 4 release candidate.
