RESUMEMATCH
7-Day Data Science Product Sprint
Resume → Job Description → Analysis → Action
PRODUCT PROMISESee how well your resume matches a job before you apply — and, more importantly, understand exactly what to change.
Objective: ship a real, public, measurable product in 7 days while producing a credible MSc Data Science portfolio project.
1. Executive Summary
ResumeMatch is a lightweight resume-to-job-description analysis product built around classical NLP rather than opaque AI scoring. The sprint prioritizes a reliable analytical engine first, then wraps it in a simple product, deploys it publicly, and validates it with real users.
Core workflow: upload a resume PDF → paste a job description → analyze → inspect match score → see matched, missing, and weak evidence → receive concrete improvement actions.
Primary analytical methods: TF-IDF, cosine similarity, n-grams, keyword extraction, skill matching, required-term coverage, and a transparent weighted scoring model.
The headline metric is 'Resume–Job Similarity' or 'Match Score', not an ATS compatibility guarantee.
The product should explain why a score was produced instead of presenting a mysterious percentage.
Analytics should focus on meaningful product events rather than page-view vanity metrics.
The final GitHub repository should include an experiment comparing a TF-IDF baseline against progressively richer hybrid scoring models.
SUCCESS DEFINITIONBy the end of Day 7: a public URL works end-to-end, common PDF/JD cases are handled, the repository documents the methodology, real users have tested it, feedback has been collected, and at least one iteration has been shipped from observed evidence.
2. Goals, Non-Goals & Guardrails
Goals
Build a functioning NLP engine before spending time on UI polish.
Make the scoring methodology reproducible and explainable.
Provide recommendations that a job applicant can immediately act on.
Deploy a free/low-friction public version.
Collect useful product feedback and failure cases.
Create an MSc-ready technical story with experiments, evaluation, limitations, and reproducible code.
Non-Goals for the 7-Day Sprint
Do not build a full generative-AI resume writer.
Do not promise that the score predicts ATS rejection or hiring outcomes.
Do not build accounts, billing, subscriptions, or complex dashboards unless the core product is already stable.
Do not make Google Analytics or a Sheets webhook a dependency for product analytics.
Do not attempt to support every document format on Day 1; prioritize common text-based PDFs.
Product Guardrails
Never claim an exact ATS score.
Clearly label the score as an internal Resume–Job Match metric.
Avoid storing uploaded resumes unless there is a clear, documented reason and consent.
Do not expose one user's resume/JD content to another user.
Gracefully reject scanned/image-only PDFs in the MVP or clearly explain the limitation.
Treat recommendations as suggestions, not guarantees of hiring success.

4. Scoring Methodology
The score should combine several measurable signals. Start with a fixed, documented weighting model; later experiments can tune the weights.

Recommended formula: Overall Match = 0.30×Keyword Coverage + 0.30×TF-IDF Similarity + 0.20×Skills Overlap + 0.10×Required-Term Coverage + 0.10×Experience/Education Terminology.
Important: normalize every component to a 0–100 scale before applying weights. Keep the raw component values in the result object so the UI can explain the score.
5. NLP Engine Architecture
The analytical pipeline should be deterministic and testable:
Input validation — verify PDF type, file size, extracted text length, and JD length.
PDF extraction — use a robust text extraction library such as pdfplumber for text-based PDFs.
Text normalization — lowercase where appropriate, normalize whitespace, remove obvious artifacts while preserving meaningful terms.
Tokenization / sentence processing — split text into usable units.
Stop-word handling — remove common function words for analytical features, but retain original text for evidence display.
N-gram extraction — identify useful phrases such as 'machine learning', 'data analysis', 'power bi', and 'cloud computing'.
TF-IDF vectorization — represent resume and JD using a shared vocabulary.
Cosine similarity — establish the baseline lexical similarity signal.
Skill/entity detection — identify technical skills, tools, technologies, role terminology, education terminology, and selected domain terms.
Comparison — classify relevant terms as matched, missing, or weakly evidenced.
Scoring — calculate each component and combine them using the documented weights.
Recommendation generation — translate analytical gaps into prioritized, human-readable actions.
Matched / Missing / Weak Evidence
Matched: the resume contains a relevant skill or phrase with reasonable evidence.
Missing: a relevant job requirement is not detected in the resume.
Weak evidence: the resume contains a generic concept but does not clearly demonstrate the specific requirement.
WEAK-EVIDENCE EXAMPLEResume: 'Worked with databases.'  |  Job description: 'PostgreSQL experience required.'  |  Classification: Weak evidence. Recommendation: explicitly name PostgreSQL if the applicant genuinely used it and add a concrete example.

8. MSc Data Science Experiment Plan
The portfolio value increases substantially if the project measures whether the hybrid scoring approach is better than a simple lexical baseline.
Research question
How effectively can classical NLP techniques measure lexical and semantic alignment between a resume and a job description, and does a weighted hybrid model provide a more useful assessment than TF-IDF similarity alone?
Experimental comparison
Model
Signals
Purpose
Expected limitation
Baseline A
TF-IDF + cosine similarity
Simple classical NLP baseline
Can miss explicit skill requirements
Baseline B
TF-IDF + keyword coverage
Adds lexical requirement awareness
Still weak on skill equivalence/context
Hybrid
TF-IDF + keywords + skills + required terms + terminology
Transparent multi-signal model
Depends on dictionaries/rules and weighting
Dataset plan
Target 50–100 synthetic or carefully constructed resume/JD pairs for the initial experiment.
Include strong matches, partial matches, weak matches, and unrelated pairs.
Avoid using real people's private resumes without permission.
Create a human relevance label for each pair, for example 0–3: unrelated, weak, moderate, strong.
Keep the dataset and labeling methodology versioned in the repository.
Evaluation metrics
Correlation between model score and human relevance rating.
Ranking quality: whether strong matches appear above weak matches.
Precision/recall or F1 for detected required skills, if a labeled skill set is available.
Ablation analysis: remove one signal at a time and observe performance changes.
Error analysis: inspect false positives, false negatives, and weak-evidence cases.
Weight experiments
Start with 30/30/20/10/10 weights.
Test a small number of alternative weight configurations rather than brute-forcing hundreds without a rationale.
Compare performance and interpretability.
Document the final choice and why it was selected.
